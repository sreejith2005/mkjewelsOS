# Forms/FMS customer integration design

Date: 2026-10-27, Asia/Kolkata. Status: **owner approved; implemented locally; release gates remain separate**.

## Intent and authority

Make customer answers from existing Forms/FMS work attributable and searchable in the existing CRM customer profile, without changing delegation, routing, completion, notifications or the customer master. CRM remains the authoritative customer home. JewelOS keeps original operational records. The user's attached master request defines phases A-H and the acceptance scenarios; this document makes the proposed implementation reviewable.

## Approaches and proposed choice

1. **Recommended: dedicated immutable customer outbox inside the existing sync architecture.** Add `crm_sync.customer_events` with service-only claim/finish contracts and reuse existing secret handling, bounded batches, backoff and diagnostics patterns. Extend the CRM receiver with an isolated customer kind. A dedicated `crm-customer-sync` sender cannot consume/coalesce staff/master events. This preserves history without changing existing roster delivery.
2. Extend the shared snapshot outbox itself. This requires changing its one-open-event-per-aggregate uniqueness, claim-time snapshots, dispatcher and finish contracts. It creates unnecessary roster/dropdown regression risk and can coalesce legitimate customer attempts; reject for this use.

Direct browser-to-two-project writes and a second customer master violate the request and are not alternatives. The recommended choice is an engineering proposal, not recorded owner approval.

## Proposed contracts and data ownership

Names below are proposed implementation names. Final SQL types/signatures must be confirmed against the reconciled baseline before writing migrations.

### JewelOS: mapping, capture and delivery

- Add versioned integration configuration and field mappings under existing Forms ownership. Proposed tables: `form_customer_mapping_versions` and `form_customer_field_mappings`, tenant-scoped, RLS-protected, minimal grants, saved/published through audited Forms management RPCs using existing permission resolution. Published mapping versions are immutable; an approved replacement applies prospectively. Existing published forms can acquire a separately approved integration binding without changing pinned form content. Revisions copy to a draft mapping requiring review.
- Mapping key is `(template_id, mapping_version, field_key)`, never label alone. Modes: operational, profile, history, both. Reusable destination catalog in `packages/core/src/forms` allows typed existing CRM fields, structured preferences/attributes, contact/follow-up evidence and explicit commercial evidence references. User/assignee questions remain operational metadata and never become customer identities.
- Default disabled for all existing forms. The actual mapping review is in the adjacent document. Enable only reviewed bindings, including how starter identity is obtained and whether later forms inherit their workflow identity. Unknown/ambiguous mappings stay in review. Static form config is not a trusted customer UUID or verified social identity.
- Add append-only `crm_sync.customer_events`: source UUID, event type, payload/schema/mapping version, canonical payload digest, source business time, tenant, instance/visit/submission/log identities, protected customer answer subset, delivery lease/attempt/dead/error category fields. Event identity is unique across `(source project, source event type, source record ID)`; do not key by template/stage definition/customer.
- Separate immutable payload from mutable delivery state, or enforce a trigger preventing payload edits. Technical retries reuse the source UUID and byte-equivalent canonical logical payload. Genuine distinct submission/visit/log IDs always remain distinct events.
- Use deferred transactional capture after successful form/visit mutations so initial submissions inserted before their instance exists can resolve their final links at transaction end. Capture submission evidence and stage completion separately. Do not call HTTP inside triggers/RPCs. Existing operational validation failures roll back capture as well. A transport outage never affects FMS commit.
- Deferred capture must resolve the mapping version pinned by the submission transaction, not whatever mapping exists at later delivery. Snapshot exact question key/label/type, selected option value/label, original and normalized answer and template family/version. Unknown nested values survive as protected evidence if mapped to history. Exclude absent, hidden and out-of-section questions; do not turn omissions into clears. File references remain opaque protected references, never permanent signed URLs or copied file bytes.
- Completion metadata comes from authoritative visit/log/assignment records: actual actor separately from assigned users and selected/effective successor, source stage key/name, actual completion time, flow version/family, execution/parallel identity and cancellation/completion state. A submission can precede completion; never label it a completed contact solely because a form was saved.
- Add `crm_sync.customer_workflow_links` with opaque CRM client UUID, verified acknowledgement and source workflow lineage; it is a link, not a customer profile mirror. Sender finish records receiver outcome/link in a protected server transaction. Existing FMS work read authorization gates any client-link read. Child workflow inherits only from a verified persisted parent relation. Existing workflows need no CRM response to progress.
- Proposed service RPCs: `crm_sync_claim_customer_events`, `crm_sync_finish_customer_event`. Claim bounded events with expiring lease and `SKIP LOCKED`; finish requires current lease token, preventing stale workers acknowledging another lease. Backoff capped, maximum attempts -> visible dead state. Invalid payload becomes diagnosable, not silently ignored. A distinct reviewed retry operation is audited and permission-scoped.

### CRM: resolution, ingestion and projections

- Extend `sync-receive` with `customer.events`, strict per-event/batch byte limits and schema versions, secret verification before parsing, sanitized failure codes only. `crm_apply_customer_event` is service-only, authorizes configured source-project/tenant mapping and resolves synced staff/branch attribution; it must not grant a fabricated actor authority. Preserve historical inactive actor IDs as evidence without restoring access. Unknown actor/branch mappings wait for review/retry.
- CRM private source identities store `(source project, tenant, provider/account scope, identity type, normalized value)` and verification/link evidence; scoped indexes prevent cross-account collisions. Instagram handle/email alone is not verification; shared or conflicting identities generate review candidates. Receiver service access does not imply arbitrary tenant/branch authority.
- Resolution order: exact authorized CRM ID; verified linked external identity; one unambiguous normalized phone across primary/alternate/billing index; validated scoped channel/email; otherwise create through the existing MKC identity path. Lock identity keys or use an equivalent uniqueness/serialization contract so concurrent events cannot create duplicates. Existing phone normalization retains country identity; never universal last-ten-digit matching.
- Multiple phone candidates stay in protected review with the original event and candidate IDs. Do not automatically merge or create an additional identity while ambiguity remains unresolved. Later events for the same source journey wait behind this identity decision, including out-of-order events. A source journey maps to one client unless an explicit audited correction is approved. New conflicting identity hints never silently retarget an established journey.
- **Walk-in exception preserved:** October 23 phone-based intake uses latest visited matching profile; explicit profile actions retain the chosen ID. Do not apply the new non-walk-in review behavior to that approved flow. Keep its cumulative shared-phone answer behavior and original identities.
- Proposed private tables: external identities, external workflow journeys, immutable customer contributions/answers, projection decisions, identity review queue. Extend existing `crm_private.sync_inbox` compatibly or use a customer-specific child record with canonical digest/result. Same event ID + same payload returns original result; same ID + conflicting payload is rejected. Inbox, identity, contribution, projection and audit changes commit together.
- Reuse existing `clients`, `leads`, `crm_contacts`, `crm_client_activity`, `lead_profile_contributions` patterns rather than replacing them. Contact evidence is separate from stage evidence. Only reviewed explicit contact outcomes set `is_contact`; assigning work/checking an operational checklist is not contact. Failed attempts remain history without inventing a successful call.
- Existing typed destinations include names/phone, city, DOB, anniversary and communication preference. Budget, product interest, occasion and future questions may use structured typed attributes/contributions rather than new columns per question. Marketing consent/opt-out is a separate explicitly sourced contract, never inferred from generic contact preference.
- Projection order: store source precedence over channel source; within a source authority level use original answer time, stable source sequence when present and source event ID for deterministic ties. Retain each loser and reason. Blank does not overwrite nonblank. CRM edits remain authoritative under the existing explicit-edit rules. Do not stamp delivery time as business time or write an old contribution directly into `clients` in a way that falsely advances `profile_updated_at`. Extend cumulative reads to use true contribution clocks and preserve existing walk-in/edit ordering.
- Extend incremental `crm_client_browse_state` and existing activity/search RPCs for source identities/FMS references. One bounded server query per list page; default existing 50-row UI paging retained. Journey and answer history use `(business_time, source_id)` cursor pages with indexed client/instance/visit IDs; no all-customer history download.
- Keep lifecycle enum (`lead`, `engaged`, `visited`, `purchased`) and existing record_type filters compatible. Expose commercial classification separately: buyer, repair-only, non-buyer/prospect, unknown; derive from verified existing visit/transaction evidence. Preserve mixed order/repair/purchase outcomes. A stage status or free-text purchase assertion stays unverified event evidence and cannot increment totals or purchase dates. No sales ledger is invented.

## Builder review: explicit policy proposals

A fresh read-only builder review identified four decisions needed to make this plan implementable. The following are conservative engineering proposals for approval with this document; they are not assumed owner decisions.

1. **Automation authority.** Completing assigned FMS work never implies CRM write authority. For automatic identity creation, profile contribution or history ingestion, require a trusted source/tenant/branch mapping, approved integration mapping, and an active linked CRM actor authorized under the existing CRM write rule for the affected record/branch. A salesperson crossing that boundary, an actor without CRM rights, or deactivation before ingestion leaves the immutable event in authorized-review state; FMS completion still succeeds. A CRM administrator with authority for that branch can explicitly approve a reviewed contribution. The review actor authorizes the CRM mutation; the original FMS actor, assigned users, source branch and time remain separate evidence. Historical inactive staff can be attributed by verified IDs during an explicitly authorized backfill, without restoring their access. No automatic contribution bypasses a denied branch rule merely because the caller is service_role. Test create, profile and history allow/deny paths separately.
2. **Mapping trust.** CRM maintains a fixed server destination/type/authority allowlist and an immutable approved-mapping registry keyed by source project, tenant, template UUID/version, mapping version and canonical descriptor digest. JewelOS authoring approval alone cannot widen that allowlist. The source sends a metadata-only mapping descriptor before data events; a permitted CRM integration administrator reviews and approves its digest using an audited CRM RPC. Until then data waits as mapping-unapproved. The receiver compares the event to the registry, checks source scope and type constraints and rejects caller-supplied authority escalation. Published registry records cannot be edited; replacement needs a new version/approval. Expose this within the existing integration administration surface rather than requiring manual SQL.
3. **Identity-review outcomes.** Initial unresolved events permit: attach to an authorized existing client; explicitly create a distinct identity despite shared phone; verify/link a scoped external identity after recording evidence; or reject with an audited reason while retaining source evidence. A review transaction locks the journey and candidate keys, records the reviewer and decision version, then releases downstream events for that journey. Exact replays cannot create another decision/customer. Correction of an already accepted attribution must be a separate privileged operation with preview/counts, reason and explicit affected event IDs, never a silent link overwrite or customer merge. Record append-only attribution amendments; rebuild only the affected clients' projections/activity linkage while retaining original event receipts and evidence in protected audit. Issue a newer link acknowledgement revision so old acknowledgements cannot retarget JewelOS links. The immutable original ingestion receipt and latest attribution revision are separate response fields. Corrections are disabled until their authorization/preview/replay tests pass.
4. **Export ownership.** CRM exports include only customer fields/evidence it owns and received mapped answers. Full original form/stage exports run in JewelOS through its existing protected report/export path, with export authority AND source-work read checks on every selected row, revalidated when the job executes. They may include explicitly selected operational answers without copying them into CRM. A CRM customer-profile export cannot fetch additional restricted answers using service credentials. The UI labels customer-only versus original stage exports and denies unavailable scope. Both paths preserve source snapshots and neutralize formulas; neither widens deep-link/work authorization.

## Backfill and cleanup

Implement an audited, restartable dry run over successful original submissions joined to exact workflow visits and snapshots. An approved mapping for the historical template version is mandatory. Snapshot hashes, source IDs and a cursor define each reviewed batch; apply rejects drift. Technical/demo exclusions must be explicit reviewed IDs/criteria, not label heuristics that might exclude real customers. Unattributed rows go to review. Reuse the live event identity/digest to avoid duplicates across capture/backfill; no original operational row edits.

Reconcile selected source count = emitted + already-ingested + pending-review + excluded + invalid, with explicit mutually exclusive categories, and compare receiver accepted counts and digest sets. Source event timestamps are preserved; no artificial current-date contacts or purchase dates. Production backfill and every destructive cleanup require separate approval. Cleanup candidates and archive/restore prerequisites are in the inventory; no deletion is recommended now.
